## 크루 운영 플랫폼 — 제작 기준 v0.4

작성일: 2026-11-10
이번 개정: 전체 서비스 설계와 개별 작업 스케치의 역할 분리. 기능 추가 없이 탐색·페이지 구조를 개편한다.

### 1. 이번부터 사용할 기준

이 묶음은 기존 v0.3 명세서, 스케치 v0.2, 이전 UI 구조 개편 v0.1을 코딩 입력으로 함께 읽어야 하는 보충 문서가 아니다. 필요한 업무 규칙을 이관한 **새 제작 기준 묶음**이다. 기존 자료는 이력으로 보관하고 이번 제작 입력에서는 제외한다.

| 파일 | 결정하는 것 | 결정하지 않는 것 |
|---|---|---|
| 00_START_HERE.md | 범위·문서 역할·충돌 처리·사용법 | 화면별 픽셀 배치 |
| 01_SERVICE_DESIGN.md | 서비스 계층·메뉴·페이지·탐색·공통 구성·확장 위치 | 제출·저장 규칙 변경 |
| 02_FUNCTION_RULES.md | 역할·기능 F-01~11·데이터·저장·예외·테스트 T-01~12 | 모든 화면의 동일한 레이아웃 |
| 03_TASK_SKETCHES.md | 개별 작업 안의 정보 순서·행동·결과 | 전체 서비스 메뉴·영구적인 화면 틀 |
| 04_CODING_HANDOFF.md | 기존 코드에 적용할 요청·기준 전환 확인·단계별 완료 판단 | 기존 코드를 읽지 않은 재생성 |

문서 역할은 상하 순위만으로 해결하지 않는다. **업무 규칙은 02, 전체 구조는 01, 작업 내부 표현은 03**을 따른다. 작업 스케치가 전체 서비스 구조를 고정하지 않는다. 업무 규칙과 탐색 설계가 실제로 양립하지 않으면 영향을 받는 기능 ID·화면 ID를 제시하고 해결한다.

### 3. 이번 구현 범위

- 전체 서비스 계층과 주요 다섯 페이지를 실제로 연결: 서비스 홈, 크루 홈, 미션 목록, 미션 상세, 퀵 리뷰.
- 미션 등록과 알림 예시를 기존 업무와 연결해 보존.
- 현재 구현된 기능과 저장 데이터를 먼저 확인하고 보존한다.
- 기본 1차 기능은 F-01~06, F-08 공통 집계 계산, F-11A. 미구현 상태의 F-07~09는 2차, F-10·F-11B는 3차로 유지한다.
- 홈·크루 홈은 기존 업무 데이터의 조회 화면이다. 추천·평가·랭킹·매출 추정 기능을 추가하지 않는다.
- 미래 기능의 위치는 설계하되 작동하지 않는 빈 메뉴를 모두 노출하지 않는다.
- 기존 구현에 2·3차 기능이 이미 있으면 임의로 삭제·숨김 처리하지 않고 새 구조에 연결한다.

### 4. 코딩 도구에 제공하는 방법

다음 중 하나만 제공한다. 동일 내용의 통합본과 개별 문서를 중복 첨부하지 않는다.

- 간편 방식: `CREW_BUILD_BRIEF_v04.md` 통합본 + 현재 프로토타입 소스.
- 분리 방식: ZIP을 풀어 00~04 파일 + 현재 프로토타입 소스. 프로젝트 파일로 관리할 때 권장.

자료의 링크만으로 본문에 접근된다고 가정하지 않는다. 가능하면 파일을 첨부하거나 작업 공간에 두고 실제로 읽게 한다. ZIP을 직접 읽지 못하는 도구에서는 압축을 풀어 제공한다.

공유된 프로토타입 URL은 화면 확인용이다. 현재 코드를 편집할 권한·파일·프로젝트 접근을 대체하지 않는다. 기존 코드가 있는 대화에서 진행하거나, 새 대화라면 소스와 실행 정보·현재 저장 형식을 함께 전달한다.

### 5. 보관·적용 상태

기존 Google Docs, 스케치, Claude 프로토타입은 삭제하거나 변경하지 않았다. 이 묶음을 Drive에 저장하는 것만으로 Claude 프로젝트 자료나 기존 코드가 자동 교체되지 않는다. 사용자가 제작 환경에 새 묶음을 전달하고 아래 기준 전환 요청을 실행해야 한다.

## 전체 서비스 설계 v0.4

### 1. 서비스 정의와 설계 원칙

크루장과 크루원이 카테고리별 크루에서 미션·피드백·소통을 이어가고, 관리자는 같은 업무 기록을 여러 크루·개인 단위로 확인하는 웹 서비스다. 강의 판매·마켓플레이스·광고 캠페인 전체 운영을 이번 범위에 추가하지 않는다.

설계는 `서비스 전체 → 크루 공간 → 개별 미션 → 작업`의 네 계층을 따른다. **퀵 리뷰는 특정 미션에 속한 작업 화면이다. 서비스 전체의 기본 화면 틀이 아니다.**

확장성은 빈 메뉴가 많다는 뜻이 아니다. 새 기능을 붙일 때 위치·대상·접근 범위·원본 데이터를 정할 수 있고 기존 업무 화면 전체를 다시 짤 필요가 줄어드는 구조를 뜻한다. 모든 미래 기능에 대한 무수정 확장을 보장하지 않는다.

### 2. 정보 구조

```text
서비스 홈 [P-01]
├─ 내 다음 행동 → 해당 미션 상세 또는 퀵 리뷰
└─ 내 크루 → 크루 홈 [P-02]

크루 공간
├─ 크루 홈 [P-02]
├─ 미션 목록 [P-03]
│  ├─ 미션 등록 [P-06, 크루장]
│  └─ 미션 상세 [P-04]
│     ├─ 안내·기한·역할별 진행 정보
│     ├─ 내 제출·피드백·입력 영역 [크루원]
│     ├─ 퀵 리뷰 작업 화면 [P-05, 크루장]
│     └─ 게시·성과 기록 [P-07, 2차]
└─ 크루 소통 [P-08, 3차]
   └─ 게시글·댓글 → 권한 있는 관련 미션

운영 관리 [관리자, 2차]
├─ 전체 크루 [P-09]
│  └─ 선택 크루의 구성원
└─ 크리에이터 상세 [P-10]
   ├─ 활동
   ├─ 콘텐츠 성과
   └─ 광고·커머스 제안 이력

시연 도구 [P-11, 공통 보조 영역]
├─ 예시 사용자·역할 전환 / 초기화
└─ 알림 미리보기 → 연결된 대상·미션·제출 버전
```

일반 크루원에게 구성원별 성장·제안 정보를 노출하는 메뉴는 만들지 않는다. 공개 구성원 명단이 필요하면 별도 범위·개인정보 확인 후 추가한다. 관리자 구성원 조회는 기존 F-08에 포함된다.

### 3. 전역 메뉴와 크루 내부 메뉴

| 위치 | 표시 내용 | 범위 |
|---|---|---|
| 전역 헤더 | CREW 홈, 내 크루, 현재 예시 사용자·역할 | 크루장·크루원 |
| 전역 운영 진입 | 운영 관리 | 해당 화면이 구현된 관리자 |
| 크루 맥락 | 선택한 크루명·카테고리, 크루 홈·미션·구현된 소통 | 접근 가능한 크루 안에서만 |
| 미션 맥락 | 크루명 / 미션 목록 / 미션 제목 / 퀵 리뷰 | 선택 미션의 현재 위치 표시 |
| 시연 도구 | 예시 사용자·초기화·알림 예시 | 접을 수 있는 보조 영역. 실제 로그인·발송으로 표현하지 않음 |

같은 미션 목록을 전역과 크루 내부에 독립적으로 중복 생성하지 않는다. '내 크루'는 한 크루만 있으면 그 크루로 바로 이동하고, 허용된 복수 크루가 있으면 접근 가능한 선택 목록을 제공한다. 이번 데이터에서 크루장·크루원의 소속은 사전 등록된 범위를 유지한다.

초기 메뉴가 적으면 상단 메뉴를 사용한다. 향후 운영 관리에 사이드바가 필요하면 그 영역에서 사용한다. 서비스 전체를 일괄적으로 사이드바 없는 화면 또는 병렬 화면으로 강제하지 않는다.

### 4. 핵심 다섯 페이지

#### P-01 서비스 홈

**목적:** 로그인 대신 선택한 예시 사용자에게 다음 행동과 크루 진입점을 보여준다.

```text
[CREW] [내 크루]                         [예시 사용자·역할]

사용자 인사 / 현재 해야 할 일
미션명 · 상태 · 기한                       [다음 행동]
미션명 · 상태 · 기한                       [다음 행동]

내 크루: 푸드 A / 크루장                  [크루로 이동]
```

- 크루원: 자신의 보완 요청·미제출 미션만 행동 목록에 표시한다.
- 크루장: 검토 대기 제출물이 있는 미션을 보여준다. 버튼은 미션 ID를 포함해 P-05로 바로 이동한다.
- 홈에서 작업 바로가기를 제공해도 퀵 리뷰의 소속·돌아갈 경로는 해당 미션으로 유지한다.
- 제작 가정: 행동 목록은 미션 마감 오름차순, 동률은 안정적인 ID 순서. 과거 기한을 숨기지 않는다.
- 할 일이 없으면 완료 점수·추천을 꾸며 넣지 않고 빈 상태와 크루 이동을 제공한다.
- 관리자 시작점은 운영 관리 구현 여부에 따른다. 미구현 단계에서 관리자에게 다른 역할의 실제 권한을 주지 않는다.

#### P-02 크루 홈

**목적:** 현재 크루의 맥락과 활동 진입점을 제공한다. 개인별 다음 행동을 모으는 P-01과 역할이 다르다.

```text
[전역 헤더]
푸드 A 크루 / 크루장 지훈
[크루 홈] [미션] [소통: 구현된 경우]

현재 크루 소개·운영 맥락
최근 미션 요약                             [미션 전체 보기]
공지 요약                                  [소통 보기, 3차]
```

- 미션 요약은 사용자에게 보이는 미션만 최근 생성순으로 표시한다. 남의 비공개 제출·성과를 크루 홈에서 우회 노출하지 않는다.
- 공지가 아직 구현되지 않았으면 공지 영역을 생략한다. 실제 없는 글·활동·구성원 수를 꾸며 넣지 않는다.
- 크루의 설명·리더는 사전 등록된 크루 데이터로 표시한다. 크루 관리·편집·신규 생성 기능을 추가하지 않는다.
- 크루가 하나여도 이 공간의 역할은 유지하되 불필요한 선택 절차는 생략한다.

#### P-03 미션 목록

**목적:** 여러 미션을 둘러보고 선택한다. 선택한 상세를 영구적인 오른쪽 패널로 붙이지 않는다.

```text
[크루 맥락과 메뉴]
미션                                      [미션 등록, 크루장]
미션 카드 또는 행: 제목 / 목적 / 기한 / 형식 / 역할별 상태
[미션 보기]  [미션 보기]  [미션 보기]
```

- 크루원은 자신의 상태를, 크루장은 미션별 대상·검토 대기 수를 본다.
- 카드형은 기본 제안이다. 썸네일 없이 제목·상태·기한 중심으로도 성립해야 한다.
- 목록 조회 필터는 전체 / 내 할 일 / 완료(크루원), 전체 / 검토할 미션(크루장). 기존 데이터에서 계산하며 새 업무 상태를 만들지 않는다.
- 기본 목록은 최근 생성순을 제작 가정으로 한다. 기존 코드의 다른 정렬이 있으면 변경을 명시한다.
- 0·1·여러 미션과 긴 제목에서 배치가 성립해야 한다. 실제 저장 데이터에 시연용 미션을 몰래 추가하지 않는다.
- 미션 등록 후에는 기존 기능대로 해당 미션 퀵 리뷰로 이동한다. P-04로 돌아갈 경로를 함께 제공한다.

#### P-04 미션 상세

**목적:** 선택한 미션의 안내·상태·관련 작업을 연결하는 중심 페이지.

```text
[크루명 / 미션 목록 / 미션 제목]
미션 제목 · 기한 · 제출 형식

크루원: 다음 행동 → 내 피드백 → 기준 → 제출·수정 폼 → 이력
크루장: 기준·대상·상태별 현황 → [퀵 리뷰 열기]

완료 결과물: [게시·성과 기록, 2차 구현 후]
```

- PC에서도 크루원 상세에는 영구적인 왼쪽 미션 목록을 두지 않는다.
- 보완 요청은 피드백을 먼저 읽고 수정할 수 있게 한다. 검토 대기·완료는 명세에 따른 읽기 전용 상태다.
- 피드백·제출의 상태별 장면을 서로 독립된 데이터 페이지로 복제하지 않는다. 같은 상세가 최신 상태와 이력을 표현한다.
- 미션 상세 안에서 퀵 리뷰로 진입하되, 리뷰 영역을 작은 카드 안의 중첩 화면으로 가두지 않는다.

#### P-05 퀵 리뷰

**목적:** 해당 미션의 여러 제출물을 효율적으로 검토하는 전용 작업 페이지.

```text
[크루명 / 미션 목록 / 미션 제목 / 퀵 리뷰]
[미션 상세로 돌아가기]
상태 필터
제출자 목록 | 선택 제출물 · 버전 · 이전 피드백 · 처리 폼
```

- 이 페이지에서만 목록·상세 병렬 구조를 기본으로 사용한다.
- 넓은 작업 폭을 쓰되 전역 메뉴·크루·미션 맥락을 잃지 않는다.
- `missionId` 없이 퀵 리뷰에 진입하지 않는다. 유효하지 않은 미션이면 접근 가능한 목록으로 안내한다.
- 처리 직후 읽기 전용 결과, 다음 대상 이동, 빈 목록, 과거 피드백 보존은 02의 F-04~06을 따른다.
- 모바일에서는 상태 필터→제출자 선택→상세 순으로 세로 배치한다.

### 5. 나머지 기능을 붙일 위치

| 기능 | 연결 위치 | 계층·단계 |
|---|---|---|
| 미션 등록 | P-03 등록 버튼 → P-06 | 크루 하위 작업, 1차 |
| 피드백 알림 | P-11 → 해당 크루원 P-04의 연결 버전 | 1차, 실제 발송 없음 |
| 게시·성과 | 완료된 P-04 결과물 → P-07 | 미션·결과물 하위, 2차 |
| 관리자 전체 현황 | 운영 관리 → P-09 | 전역 운영 공간, 2차 |
| 개인 활동·성과·제안 | P-09 구성원 → P-10 탭 | 관리자 하위, 2차 |
| 공지·질문·댓글 | 크루 내부 소통 → P-08 | 크루 공간, 3차 |
| 미제출 알림 예시 | 담당 미션·운영 현황에서 P-11 | 3차 |

새 기능은 전역 메뉴에 무조건 추가하지 않는다. 어느 크루·사용자·미션·결과물에 속하는지부터 판단한다. 예를 들어 성과 입력과 관리자 성과 조회는 서로 다른 화면이지만 같은 기록을 참조한다.

### 6. 페이지·컴포넌트·데이터 책임

| 계층 | 예시 | 담당 책임 |
|---|---|---|
| 앱 구성 | AppShell, GlobalNavigation, CrewNavigation, DemoControls | 공통 메뉴·현재 맥락·역할별 진입점 |
| 페이지 | ServiceHome, CrewHome, MissionList, MissionDetail, MissionReview | 필요한 조회 결과를 조합하고 화면을 연결 |
| 공통 표현 | MissionCard, StatusBadge, DeadlineText, MissionCriteria, EmptyState | 같은 데이터를 일관되게 표시 |
| 작업 표현 | SubmissionForm, SubmissionHistory, FeedbackForm, ReviewQueue | 작업별 입력·오류·이력 표시 |
| 업무 규칙 | 조회·집계·제출·재제출·피드백 명령 | 권한·상태·관계·검증 |
| 저장 | 기존 로컬 저장 어댑터 | 저장 성공·실패·형식 호환 |

표의 이름은 제안이다. 기존 코드에 같은 책임이 있으면 재사용한다. 컴포넌트 분리를 위해 불필요한 라이브러리·추상화·백엔드를 도입하지 않는다.

```text
저장된 업무 기록
 → 접근 범위를 적용한 조회·집계
 → 여러 페이지에서 같은 결과를 표시

입력
 → 업무 명령 검증
 → 다음 데이터 계산
 → 저장 성공 후 공유 상태 확정
 → 홈·목록·상세·리뷰 동시 갱신
```

업무 데이터와 탐색 상태(`pageId`, `crewId`, `missionId`, 선택 제출자·필터), 미저장 폼 입력을 분리한다. 제목·이름을 ID로 사용하지 않는다. 화면별로 동일 제출물을 복제 저장하지 않는다.

### 7. 이동·접근·반응형 규칙

- 앱 내 이동은 공통 함수가 미저장 입력과 목적지 접근 범위를 확인한다. 취소하면 입력과 현재 위치를 유지한다.
- 목록 복귀 시 같은 사용자·크루 범위의 필터를 유지한다. 역할·소속 변경 시 유효하지 않은 미션·선택 대상은 해제한다.
- 미션 변경 후 이전 미션의 제출물이 상세에 남지 않는다.
- 과거 알림은 연결된 피드백을 강조하고 최신 상태를 함께 표시한다. 수정 가능 여부는 최신 상태로 판단한다.
- 페이지는 각각 독립된 화면 상태와 진입 조건을 갖는다. 모든 콘텐츠를 한 화면에 펼쳐놓고 앵커 이동만 하는 것은 이번 구조 개편 완료로 보지 않는다.
- 기존 라우터가 있으면 재사용한다. 없으면 명시적인 페이지 상태로 구현할 수 있다. 공유 URL·브라우저 뒤로가기 완전 지원은 이번 기능 보존 개편의 자동 필수 범위가 아니다. 실제 배포 전에 제공 환경에 맞춰 직접 URL·새로고침 동작을 추가 검증한다.
- 탐색 페이지는 약 1200px 최대 폭, 크루원 단일 상세는 약 840px, 퀵 리뷰는 넓은 작업 폭을 제안한다.
- 390px·1280px에서 현재 위치·필수 필드·오류·버튼이 잘리지 않게 하고 키보드 이동이 가능해야 한다.

### 8. 시각 디자인 원칙

화면의 성격에 맞는 밀도를 사용한다. 홈·목록은 여유 있게, 상세는 읽기 편하게, 퀵 리뷰는 여러 정보를 비교하기 적절하게 구성한다.

- 본문 16px, 보조 14px, 작은 메타데이터 12px, 페이지 제목 28~32px를 시작값으로 삼는다. 한국어 줄바꿈과 긴 제목을 검증한다.
- 중립 바탕·명확한 콘텐츠 면·한 가지 브랜드 강조색을 기본으로 한다. 상태·오류는 색만으로 표현하지 않는다.
- 주요 행동은 진한 채움 버튼, 보조 행동은 테두리·텍스트 버튼으로 구분한다. 모든 CTA를 같은 강조도로 만들지 않는다.
- 간격은 4px 단위, 탐색 섹션 32~48px, 항목 16~24px, 작업 영역 8~16px를 제안한다.
- 불필요한 카드 중첩을 줄이고 제목·여백·구분선으로 정보 위계를 만든다.
- 큰 소개 배너·후기·3D 이미지·강의 추천을 기능 확장의 근거로 추가하지 않는다.
- 시연 도구는 접을 수 있어야 하며 예시 사용자·실발송 없음이라는 사실은 확인 가능하게 유지한다.

### 9. 구조 개편 인수 조건 U-01~08

- U-01: 서비스 홈→크루 홈→미션 목록→상세→퀵 리뷰가 서로 구별되는 페이지로 연결된다.
- U-02: 미션 목록과 크루원 상세에 이전의 목록+상세 병렬 틀을 유지하지 않는다. 퀵 리뷰에서는 유지한다.
- U-03: 퀵 리뷰에 선택 미션 맥락과 상세·목록으로 돌아가는 경로가 있다.
- U-04: 두 개 이상의 미션을 선택·왕복해도 올바른 미션·사용자·버전이 표시된다. 테스트 데이터는 운영 예시와 분리해 사용한다.
- U-05: 같은 제출·피드백 변경이 홈·목록·상세·공통 집계에 일관되게 반영된다.
- U-06: 미래 성과·소통·제안 기능을 어디에 연결할지 설명할 수 있고, 미구현 메뉴를 작동하는 것처럼 노출하지 않는다.
- U-07: 미저장 입력 이탈·접근 불가·빈 목록·긴 제목·모바일을 확인한다.
- U-08: 기존 F 기능·T 테스트를 보존한다. 새 홈 화면 하나와 색상만 바꾸고 나머지 구조를 유지하면 개편 완료로 보지 않는다.

## 기능·데이터·검증 규칙 v0.4

작성일: 2026-11-10. F-01~11과 T-01~12는 기존 v0.3의 업무 규칙을 이관했다. 전체 화면 구조는 01_SERVICE_DESIGN.md로 교체한다.

### 목적과 범위

크루장은 미션과 제출물을 관리·피드백하고, 크루원은 다음 행동을 이해하며, 관리자는 동일 기록을 여러 크루와 개인 단위로 확인한다. 검증 대상은 핵심 업무와 사용성이다. 리텐션·교육 효과·수익성을 이 프로토타입으로 입증하지 않는다. 실제 운영 베타·외주 계약서와 구분한다.

실제 동작은 같은 브라우저의 가상 데이터 입력·저장·조회·상태 변경이다. 역할 전환과 외부 알림은 시뮬레이션이다. API·실발송·영상 업로드·모집·계약·평가·정산·캠페인 전체 운영은 보류한다.

[제작 가정]은 테스트를 위해 임시 적용하는 규칙이며 회사의 확정 운영 정책이 아니다. 현재 저장 데이터·기능이 이미 구현돼 있으면 소스를 읽고 호환성을 유지한다.

### 기존 화면 ID와 새 페이지의 연결

기능 본문의 SC 번호는 기존 기능 추적용 별칭이다. 이전 화면 배치나 영구 병렬 레이아웃을 뜻하지 않는다.

| 기존 별칭 | v0.4 연결 |
|---|---|
| SC-01 미션 목록·등록 | P-03 목록, P-06 등록, 크루장의 P-04 미션 상세 |
| SC-02 퀵 리뷰 | P-05: 선택 미션 상세에 속한 작업 화면 |
| SC-03 크루원 내 미션 | P-03 목록에서 P-04 독립 상세로 이동 |
| SC-04 게시·성과 | P-04 완료 결과물에서 P-07 |
| SC-05 소통 | 크루 공간 P-08 |
| SC-06 관리자 전체 크루 | 운영 관리 P-09 |
| SC-07 개인 상세 | P-09에서 P-10 |
| SC-08 알림 미리보기 | P-11에서 연결된 P-04 또는 해당 미션 |

서비스 홈 P-01·크루 홈 P-02는 기존 데이터의 조회 화면이다. 새 데이터 엔티티나 상태를 추가하지 않는다. 구체적인 메뉴·진입점·정렬은 01을 따른다.

### 역할과 제작 가정

#### 역할별 접근 범위

크루원: 배정된 미션, 본인 제출·피드백·게시·성과 기록. 같은 크루의 공지·질문·댓글.

크루장: 자기 크루의 미션 생성, 대상자 지정, 제출물 검토·피드백, 활동 현황, 크루 소통. 회사 내부 제안 메모는 표시하지 않는다.

관리자: 담당 크루 여러 개의 현황과 구성원·개인 활동·성과, 광고·커머스 제안 이력. 첫 버전에서는 공통 관리자 화면 하나를 사용한다.

원본의 최고 관리자·매니저 구분은 후속 권한 설계에 보존한다. 이번에는 역할 부여·크루 이동 승인·설정 화면을 만들지 않는다. 예시 사용자의 소속·담당 크루는 사전 등록한다.

상단 역할 전환은 시연 도구다. 메뉴와 예시 데이터 필터만 전환하며 실제 인증·서버 권한 검사를 구현한 것으로 표시하지 않는다. 실제 인물의 연락처·계약·수익 자료를 입력하지 않는다.

#### 첫 제작에서 적용할 가정

A-01: 진행자가 한 브라우저 탭에서 예시 사용자를 전환하는 테스트. 저장은 브라우저 로컬 저장소로 하며 다른 기기·브라우저·동시 탭과 동기화하지 않는다.

A-02: 미션별 제출 형식은 텍스트 또는 링크 중 하나. 대표 시나리오는 영상 공유 링크다. 기획안 승인 후 영상 승인으로 이어지는 두 단계 검토는 제외한다.

A-03: 미션당 대상자별 결과물 1개와 수정 버전 여러 개. 주간 콘텐츠 3개 등 복수 결과물 목표는 제외한다.

A-04: 미션 생성 시 대상자를 고정한다. 이후 합류자는 기존 미션의 미제출자로 자동 추가하지 않는다. 첫 버전은 생성 후 대상·기한·형식 수정과 미션 삭제를 지원하지 않는다.

A-05: 검토 완료 후 게시 기록을 선택적으로 입력한다. 텍스트·링크 미션 모두 게시 기록 없이 완료 상태를 유지한다. 이미 게시된 콘텐츠의 사후 검토와 완료 후 재개방은 후속 확인한다.

A-06: 마감 이후에도 제출·재제출을 허용하고 ‘기한 후 제출’을 표시한다. 별도 재제출 마감, 자동 종료, 벌점은 적용하지 않는다.

A-07: 과제·피드백은 본인·담당 크루장·담당 관리자에게만 표시한다. 게시글·댓글은 같은 크루에 공개한다. 동료의 개인 성장 지표 공개는 이번 범위에서 제외한다.

원본의 상시 영입·정원 15명·성인 참여·4주 온보딩 등 정책은 원본의 확정 표기를 보존한다. 이번 제작은 사전 구성한 크루를 사용하므로 모집·연령 확인·온보딩 자동화를 만들지 않는다.



### 기능 명세

#### F-01 역할 전환·저장·초기화

사용자·화면: 진행자 / 공통 시연 영역. 역할과 함께 실제 예시 사용자(민지·하늘·소라·지훈·유진·서연 등)를 선택한다. 선택한 사용자에서 역할·소속·담당 크루를 결정하고 불일치 조합은 허용하지 않는다.

동작: 역할·소속에 맞는 시작 화면과 메뉴로 이동한다. 역할을 바꿔도 미션·제출·피드백·성과·제안 데이터는 동일한 저장소를 참조한다. 저장 성공한 데이터는 새로고침 후 유지한다.

예외: 저장 실패 시 성공 메시지나 상태 변경을 확정하지 않고 입력을 유지한다. 검증한 다음 상태 전체를 로컬 저장소에 기록한 후 화면 상태를 확정한다. 초기화는 확인 후 이 앱의 가상 데이터만 복원하며 다른 앱의 저장소를 지우지 않는다. 호환되지 않는 저장 버전은 자동 삭제하지 않고 초기화 안내를 표시한다.

완료 기준: 크루원이 제출한 건을 크루장이 확인하고 관리자가 같은 상태로 조회한다. 새로고침으로 저장된 기록이 사라지지 않는다.

#### F-02 미션 등록·대상 지정

사용자·화면: 크루장 / SC-01. 필수: 제목, 목표·제출 기준, 제출 형식(텍스트/링크), 마감 일시, 대상자 1명 이상. 크루는 본인 소속으로 고정한다.

동작: 자기 크루의 사전 등록 구성원 중 대상자를 고른다. 등록 즉시 대상자의 내 미션에 표시한다. 대상자는 미션 생성 시점 명단으로 저장한다. 제목·기준의 공백 입력, 대상자 없음, 잘못된 날짜는 등록을 막는다.

범위: 초안·예약 공개·반복 미션·생성 후 수정·삭제·다중 첨부는 제외. 등록된 미션이 없으면 빈 화면과 ‘미션 등록’을 제공한다.

완료 기준: 새 미션 등록 후 대상자에게만 표시되고, 대상자 전체가 미제출로 집계된다.

#### F-03 최초 제출

사용자·화면: 크루원 / SC-03. 필수: 미션이 지정한 텍스트 본문 또는 영상 공유 링크. 설명은 선택.

동작: 미션 기준·마감과 현재 상태를 먼저 보여준다. 링크는 http/https 형식만 허용하며 서버 접근 가능 여부까지 확인했다고 표시하지 않는다. 저장 시 1차 버전·제출자·시각을 기록하고 검토 대기로 바꾼다.

예외: 필수값 누락·잘못된 URL은 해당 입력 옆에 오류를 표시한다. 저장 중 버튼을 비활성화해 연속 클릭에 따른 중복 버전을 방지한다. 마감 이후는 제출을 허용하되 기한 후 표시를 남긴다.

완료 기준: 제출한 텍스트·링크·설명을 크루장 리뷰에서 확인하고, 미제출 수가 1 줄며 검토 대기 수가 1 증가한다.

#### F-04 퀵 리뷰·원본 확인

사용자·화면: 크루장 / SC-02. 상태 필터: 검토 대기, 보완 요청, 완료, 미제출. 기본은 검토 대기다.

동작: 제출자 목록과 선택한 사람의 최신 제출·버전·시각·설명·이전 피드백을 함께 보여준다. 검토 대기는 제출 시각이 빠른 순서로 정렬한다. 텍스트는 화면에서 읽고 영상 링크는 새 탭으로 연다.

처리 후: 방금 처리한 사람은 검토 대기 목록에서 제외하고, 상세에는 처리 결과를 읽기 전용으로 유지한다. 다음 대상이 있으면 ‘다음 검토 대기’를 활성화한다. 없으면 버튼을 비활성화하고 ‘남은 검토 대기 없음’을 표시한다. 필터·미션을 변경한 결과가 비어 있으면 상세도 빈 상태로 바꾼다.

완료 기준: 목록 페이지로 되돌아가지 않고 다음 제출물을 검토한다. 처리 직후의 읽기 전용 결과와, 조건 변경 후의 빈 목록을 구별한다. 이전 대상에 새 피드백을 중복 입력할 수 없고 원본 영상 임베드·자동 재생은 요구하지 않는다.

#### F-05 피드백·처리 결과

사용자·화면: 크루장 / SC-02. 입력: 완료 또는 보완 요청, 공통 문구 선택(선택), 자유 설명.

규칙: 보완 요청은 수정 방향을 필수로 받는다. 완료 설명은 선택이다. 고정 문구 3개(첫 장면·메시지 전달·다음 행동)를 자유 설명란에 삽입하고 수정할 수 있게 한다. 문구 관리 화면은 없고 1줄·100자 제한도 없다. ‘우수’는 업무 상태가 아니다.

저장: 피드백은 검토한 제출 버전·작성자·시각·처리 결과에 연결한다. 최신 버전이 검토 대기일 때만 처리한다. 결과와 F-11A 알림 예시를 함께 저장한다. 관리자 화면 제작 전에도 같은 상태 집계 계산을 검증할 수 있어야 한다.

예외·완료 기준: 빈 보완 설명은 저장되지 않는다. 이미 처리한 버전을 다시 클릭해 피드백이 중복되지 않는다. 과거 피드백의 수정·삭제는 이번 범위에서 제외한다.

#### F-06 수정·재제출

사용자·화면: 크루원 / SC-03. 조건: 본인 제출물의 최신 상태가 보완 요청. 입력: 새 텍스트/링크와 수정한 내용(필수).

동작: 이전 제출과 피드백을 먼저 보여준다. 수정본 저장 시 같은 미션·크루원의 결과물 아래 버전 번호를 증가시키고 검토 대기로 바꾼다. 과거 제출 내용과 피드백은 덮어쓰지 않는다.

예외: 검토 대기 중 임의 수정, 완료 후 재제출, 버전 삭제는 제외한다. 변경 내용이 비어 있으면 제출을 막는다. 링크가 같아도 외부 파일 수정 가능성을 고려해 형식만으로 재제출을 막지 않는다.

완료 기준: 크루장이 1차 피드백과 2차 수정 내용을 구별하고, 집계는 결과물 1건으로 유지된다.

#### F-07 게시·성과·회고 기록

사용자·화면: 크루원 / SC-04. 조건: 결과물 검토 완료. 게시·성과 기록은 선택 작업이며 입력하지 않아도 완료 상태를 유지한다. 게시 기록을 저장할 때만 플랫폼, 게시 URL, 게시일을 필수로 받으며 검토용 공유 링크와 구분한다.

성과 입력: 성과 확인일, 조회수, 회고. 조회수는 비워두거나 0 이상의 정수로 입력한다. 성과 수치 또는 회고를 남기면 확인일이 필수이고 게시일보다 앞설 수 없다. 모든 화면의 날짜·시간 표시는 한국 시간 기준이다.

동작: 결과물당 실제 게시물 1개. 게시 정보만 먼저 저장할 수 있다. 조회수·회고가 모두 비어 있으면 성과 관찰 기록을 만들지 않는다. 값이 하나라도 있으면 확인일을 필수로 받고, 같은 게시물·같은 확인일은 수정, 다른 확인일은 새 관찰 기록으로 추가한다. 빈 조회수는 null로 저장하고 0으로 변환하지 않는다.

완료 기준: 미게시·게시했으나 미집계·조회수 0을 구별한다. 관리자 개인 성과에 게시 URL·확인일·수치·회고가 연결된다. 계정 API·자동 수집·매출 추정은 하지 않는다.

#### F-08 전체 크루·개인 활동 조회

사용자·화면: 관리자 / SC-06·07. 기본 필터: 담당 크루 전체·전체 기간·전체 미션. 선택 항목: 크루 전체/개별, 미션 마감일 기준 기간, 미션 전체/개별. 기간은 한국 시간 기준 시작일 00:00 이상부터 종료일 다음 날 00:00 미만까지 포함한다.

집계: 분모는 선택된 미션들의 ‘대상자-미션’ 조합 수다. 각 조합의 최신 상태만 센다. 재제출 버전 수를 제출 인원으로 더하지 않는다. 전체 미션 조회는 단위를 ‘명’ 대신 ‘건’으로 표시한다.

이동: 전체 크루 → 크루 구성원 → 개인 상세의 활동·콘텐츠 성과·제안 이력. 활동에는 미션, 상태, 제출 버전·시각, 피드백 이력을 표시한다. 성과는 게시물별 수동 입력 기록을 보여준다.

완료 기준: 네 상태의 합계가 대상 건수와 같고 개인 기록과 일치한다. 제출·피드백 상태는 즉시 갱신하되 콘텐츠 지표는 마지막 수동 확인일을 표시한다. 자동 성장 점수·순위·수익 차트는 제외한다.

#### F-09 광고·커머스 제안 이력

사용자·화면: 관리자 / SC-07 제안 탭. 필수: 크리에이터, 제안일, 담당자, 구분(광고/커머스), 브랜드·상품명, 제안 내용, 진행 상태. 내부 메모는 선택.

상태 가정: 제안 준비, 제안 전달, 협의 중, 진행 확정, 보류, 종료. 어떤 상태로든 수동 변경할 수 있고 변경 전후 상태·담당자·시각을 기록한다. 같은 값의 재저장은 상태 변경 이력을 추가하지 않는다. ‘제안 전달’은 외부에서 전달한 사실을 사람이 기록하는 상태다.

동작: 개인별 제안 목록과 상세·내부 메모를 보여준다. 크루원·크루장 화면에는 내부 메모를 노출하지 않는다. 새 제안 등록과 상태 수정은 가능하되 삭제는 제외한다.

완료 기준: 같은 사람에게 여러 제안을 기록하고 최근 이력을 찾을 수 있다. 저장을 메시지 발송으로 표현하지 않는다. 후보 추천·수락/거절·광고주 검수·계약·정산 흐름은 구현하지 않는다.

#### F-10 크루 소통·관련 미션

사용자·화면: 크루장·크루원 / SC-05. 입력: 글 구분, 제목·본문, 관련 미션(선택). 댓글은 본문 필수.

규칙: 크루장은 공지·질문, 크루원은 질문을 작성한다. 공지는 목록 상단에서 먼저 보여주고 각 구분 안에서는 최신순으로 정렬한다. 댓글은 작성순으로 표시한다. 작성자·작성 시각을 기록한다.

연결: 작성자는 자기에게 보이는 같은 크루 미션만 연결한다. 게시글·댓글은 크루 전체에 공개하되, 미션 대상자 또는 담당 크루장만 연결 미션을 연다. 비대상자는 제목·내용 대신 ‘대상자 전용 미션’ 표시와 비활성 버튼을 본다. 화면 ID를 직접 지정해도 예시 접근 범위를 확인한다. 제출·피드백은 글에 자동 노출하지 않는다.

완료 기준: 같은 크루의 다른 예시 사용자로 전환해 글·댓글을 확인한다. 다른 크루 글은 섞이지 않는다. 실시간 채팅·첨부파일·검색·좋아요·게시글 수정/삭제는 제외한다.

#### F-11 알림 시뮬레이션

사용자·화면: 공통 / SC-08. F-11A 피드백 도착·이동은 1차에, F-11B 마감 후 미제출 안내 미리보기는 3차에 만든다. 실제 발송 기능은 없다.

F-11A 피드백: F-05 저장 시 대상자·미션·피드백 ID와 연결된 알림 예시 1개를 생성한다. ‘내 피드백 보기’는 해당 예시 크루원과 제출물로 이동하고 시연용 사용자 전환임을 표시한다. 과거 알림을 열면 연결된 버전의 피드백과 현재 상태를 함께 보여주며 수정 가능 여부는 최신 상태로 판단한다.

F-11B 미제출: 크루장은 자기 크루, 관리자는 담당 크루에서 미리보기 버튼을 사용한다. 클릭 시점에 마감이 지났고 최초 제출이 없는 대상자만 계산한다. 보완 요청자는 제외한다. 대상이 없으면 0명을 표시하고 발송 성공 문구를 보여주지 않는다.

완료 기준: 수신 대상·문구·연결 화면을 확인할 수 있다. 카카오·이메일 실발송, 자동 예약·재시도·주기적 독촉은 없다. 같은 피드백 이벤트의 중복 예시 생성을 막는다.

### 공통 상태·데이터 규칙

#### 상태 변경과 예외

미제출 → 검토 대기: 대상 크루원이 최초 제출. 검토 대기 → 보완 요청/완료: 담당 크루장이 최신 버전을 처리. 보완 요청 → 검토 대기: 크루원이 수정본을 제출.

미제출은 대상자에게 결과물이 없는 상태다. 작성 중 내용은 제출로 세지 않는다. 자동 임시저장은 제외한다. 입력 변경 후 앱 내 메뉴·대상자·미션·예시 사용자·초기화 이동 시 ‘저장하지 않고 이동할까요?’를 확인한다. 취소하면 입력을 유지하고, 이동을 승인하면 버린다. 브라우저 종료·새로고침 경고는 지원 범위에서 처리하며 입력 보존을 보장하지 않는다.

완료는 내부 검토 결과다. 실제 게시·성과 입력·제안 진행 상태와 독립적으로 저장한다. 오류로 저장하지 못한 경우 네 상태와 집계를 바꾸지 않는다.

링크 접근 불가: 크루장이 보완 요청과 ‘링크 접근 권한을 확인해 주세요’ 설명을 남긴다. 별도 오류 상태는 추가하지 않는다. 링크 형식 검사만으로 원본이 존재하거나 누구나 열 수 있다고 판단하지 않는다.

#### 최소 데이터 연결

사용자·크루·소속·관리자 담당: 예시 사용자 ID, 역할, 크루 ID, 담당 크루 ID 목록. 별도 관리 화면 없이 초기 데이터로 제공.

미션·대상자: 미션 ID, 크루 ID, 제목, 기준, 제출 형식, 마감, 생성자·시각, 고정 대상 사용자 ID 목록.

결과물·제출 버전: 미션 ID와 크루원 ID로 결과물 1개. 버전마다 본문/공유 URL, 설명·수정 내용, 제출 시각. 최신 상태와 버전 ID 유지.

피드백: 결과물·제출 버전 ID, 처리 결과, 설명, 작성자·시각. 댓글처럼 버전과 무관하게 흩어지지 않게 저장.

게시물·성과 관찰: 완료 결과물 ID, 플랫폼·게시 URL·게시일. 관찰에는 게시물 ID·확인일·조회수(null 허용)·회고·수정 시각. 수치 출처는 ‘수동’으로 표시.

제안 이력: 크리에이터 ID, 제안 ID, 제안일·담당자·유형·브랜드/상품·내용·상태·내부 메모·변경 이력.

소통·댓글: 크루 ID, 글 ID, 작성자·시각·구분·내용·관련 미션 ID. 댓글은 부모 글 ID와 연결.

알림 예시: 이벤트 ID, 대상 사용자 ID, 종류, 관련 미션·결과물·피드백 ID, 생성 시각. 외부 발송 상태는 만들지 않는다.

같은 기록을 역할마다 별도 복사해 저장하지 않는다. 집계는 원본 데이터에서 계산하고, 예시 총계를 화면에 고정 숫자로 작성하지 않는다.

### 검증 시나리오와 완료 기준

#### 재현 가능한 예시 데이터

푸드 A: 크루장 지훈, 크루원 민지·준호·하늘. 뷰티 B: 크루장 유진, 크루원 소라·유나. 관리자 서연은 두 크루 담당. 모두 가상 인물이며 실제 계정·수익을 사용하지 않는다.

크루별 대표 미션 1개. 초기 푸드 A는 민지 미제출·준호 완료·하늘 미제출, 뷰티 B는 소라 검토 대기·유나 미제출. 총 대상 5건 = 검토 대기 1 + 보완 요청 0 + 완료 1 + 미제출 3.

예시 날짜·제출 이력은 최초 실행 또는 사용자가 명시적으로 초기화할 때만 생성해 함께 저장한다. 대표 미션 기한은 생성 기준 시각보다 이전으로 설정하고 ‘시연용 기한’이라고 표시한다. 새로고침 때 날짜를 재생성하지 않는다. 실제 제출 시각·마감 비교는 당시 현재 시각을 사용한다. 새 미션은 입력한 기한을 적용한다.

#### 핵심 경로 인수 조건

- T-01: 별도 초기 상태에서 크루장이 특정 대상자에게 새 미션을 등록하면 대상자에게만 보이고, 대상자 모두 미제출로 계산된다. 확인 후 예시 데이터를 초기화하고 T-02~08을 진행한다.

- T-02: 민지 최초 제출 후 전체 집계는 검토 대기 2·보완 요청 0·완료 1·미제출 2. 민지 제출 버전은 1개다.

- T-03: 민지에게 보완 요청 후 전체 집계는 검토 대기 1·보완 요청 1·완료 1·미제출 2. 빈 수정 방향은 저장되지 않는다.

- T-04: 알림 예시로 민지의 해당 제출물에 이동한다. 수정 내용과 새 링크로 재제출하면 검토 대기 2·보완 요청 0·완료 1·미제출 2. 과거 피드백이 남는다.

- T-05: 크루장이 수정본을 완료하면 검토 대기 1·보완 요청 0·완료 2·미제출 2. 결과물 수는 증가하지 않고 제출 버전만 2개다.

- T-06: 민지가 게시 기록과 조회수 0을 저장하면 관리자 성과에 ‘0’으로 보인다. 미입력은 ‘미집계’로 구분되고 확인일도 표시된다.

- T-07: 관리자가 제안을 등록·수정하면 민지의 제안 이력에 남고, 크루장·크루원 메뉴에는 내부 메모가 보이지 않는다.

- T-08: 공지·질문·댓글을 등록하고 같은 크루 역할로 확인한다. 관련 미션 이동과 다른 크루 글 제외가 동작한다.

- T-09: 일부 구성원만 대상인 미션을 공지에 연결하면 비대상 크루원은 게시글만 읽고 연결 미션의 내용·제출물은 열 수 없다.

- T-10: 새로고침과 사용자 전환 후 저장된 예시 날짜·버전·피드백이 바뀌지 않는다. 다른 예시 크루 사용자를 고르면 데이터 범위도 바뀐다.

- T-11: 마지막 검토 대상을 처리하면 읽기 전용 결과와 ‘남은 검토 대기 없음’이 보인다. 이후 빈 필터로 이동하면 상세가 비워진다.

- T-12: 게시 정보만 저장하면 빈 성과 관찰 기록은 생기지 않는다. 조회수 0을 입력하면 관찰 기록이 생기고, 동일일 수정·다른 날짜 추가가 구분된다.

T-02~06의 기대 집계는 초기화 후 대표 미션 두 개만 있는 상태를 기준으로 한다. T-01의 추가 미션은 남기지 않는다. 1차에서는 공통 집계 함수 결과를 검증하고, 관리자 화면 구현 후 같은 수치가 보이는지 재확인한다.

#### 공통 확인

잘못된 URL, 누락된 필수값, 음수·소수 조회수, 게시일보다 이른 확인일을 저장하지 않는다. URL은 http/https만 허용한다.

연속 클릭으로 제출·피드백이 중복되지 않는다. 빈 목록·저장 실패·초기화 취소를 확인한다.

역할 전환과 새로고침 후 상태·버전·관찰 기록·메모가 일치한다. 초기화하면 원래 예시로 돌아온다.

PC와 모바일 폭에서 핵심 입력·버튼이 잘리지 않고, 상태는 색만으로 구분하지 않는다. 키보드로 입력과 주요 버튼을 사용할 수 있다.

사용자 관찰: 크루장은 검토 대상을 찾고 수정본을 구별하는가, 크루원은 수정할 내용을 자신의 말로 설명하는가, 관리자는 필요한 개인 이력을 찾는가. 성공 여부·막힌 지점·진행자 도움·소요 시간을 기록한다. 효과 수치는 테스트 전 확정하지 않는다.



### 후속 확인과 실제 운영 전환

Q-01 검토 대상·순서: 기획안과 제작물 중 무엇이 핵심이며, 두 단계 승인 또는 게시 후 피드백이 필요한가? 첫 프로토타입은 단일 검토 흐름으로 진행.

Q-02 운영 규칙: 미션당 복수 결과물, 재제출 기한, 완료 후 수정, 중간 합류자의 대상 포함 규칙이 필요한가? 테스트에서 실제 사례를 수집.

Q-03 공개 범위·담당자: 동료 성장 지표 공개, 관리자 대행 피드백, 복수 담당 매니저의 수정 권한을 확인. 첫 버전의 메뉴 분리는 보안 검증으로 간주하지 않음.

Q-04 주변 업무: 출석·온라인 모임 링크·자료 관리 중 첫 실제 운영에 필수인 항목을 확인. 우선 외부 도구·공지로 처리 가능 여부 판단.

Q-05 운영 환경: 각자 기기에서 실제 데이터를 쓰기 전 공용 저장소, 로그인·서버 권한, 백업·오류 대응, 개인정보 처리 범위 등을 별도 구현·검증. 실제 카카오 발송과 API는 연동 조건·비용·실패 대응 확인 후 결정.

Q-06 사업 정책: 계약·수익 배분·평가·제재는 원본 정책 자료로 유지. 이번 프로토타입의 피드백 횟수·응답 시간만으로 보상이나 평가를 자동 결정하지 않음.

상기 질문은 첫 제작을 멈추기 위한 조건이 아니다. 제작 가정으로 테스트를 진행하고, 확인 결과가 바뀌면 영향받는 기능 ID와 상태·데이터·화면을 함께 수정한다.

### 제작 순서와 완료 구분

이번 개편은 현재 소스에 적용한다. 기존 F-01~06, F-08 계산 부분, F-11A를 보존하고 P-01~05의 구조로 재배치한다. F-02 등록·F-11A 이동을 화면 개편 중 누락하지 않는다.

1차 기능의 검사: T-01~05, T-10·11, 저장 실패·중복 처리와 공통 검증. 관리자 화면이 없어도 집계 함수를 확인한다.
2차 추가 범위: F-07~09. 관리자 결과와 T-06·07·12 확인.
3차 추가 범위: F-10·F-11B. T-08·09와 통합 검증.
이미 구현된 이후 기능은 유지하며 새 구조에 연결한다. 아직 없는 이후 기능은 자동 구현하지 않는다.

전체 구조 완료는 01의 U-01~08, 기존 기능 보존은 이 문서의 T·공통 검증으로 판단한다. 화면이 예쁘게 바뀌었다고 기능 회귀 검사를 통과한 것으로 보지 않는다. 타입 검사·빌드·관련 테스트와 실제 브라우저 확인 결과를 구분한다.

### 기술·저장·구현 원칙

현재 프로젝트의 프레임워크·라우터·패키지 관리자·스타일 도구를 먼저 확인하고 유지한다. 신규 프로젝트가 필요한 별도 상황의 기존 권장안은 React + TypeScript + Vite, 일반 CSS/CSS Modules, Context + useReducer, localStorage, Vitest이다. 이 UI 개편을 이유로 기술 스택을 바꾸거나 서버·인증을 추가하지 않는다.

업무 상태 전환 함수는 다음 데이터를 계산하고, 중앙 명령 처리에서 검증·저장을 수행한다. 저장에 성공한 뒤 화면 상태를 확정하고 실패하면 이전 업무 상태와 폼 입력을 유지한다. 직접 UI 컴포넌트 곳곳에서 저장·집계를 수행하지 않는다.

미션·사용자·결과물·제출 버전·피드백·역할·상태의 ID와 타입을 유지한다. 화면 변경 때문에 업무 데이터 복사본을 만들거나 과거 제출을 덮어쓰지 않는다. 최초 실행 또는 확인받은 초기화에서만 시드 데이터·날짜를 만든다. 렌더링·새로고침으로 알림·이력·시드를 재생성하지 않는다.

문서 버전과 저장 schemaVersion은 별개다. 레이아웃 변경만으로 저장 키·형식을 변경하지 않는다. 불가피한 변경은 읽기 호환·변환·백업·실패 복구를 구체화한다. 호환되지 않는 데이터를 자동 삭제해 해결하지 않는다.

기존 테스트가 있으면 활용한다. 상태 전환·집계·저장 실패의 핵심 규칙을 의미 있게 검증하고 실제 화면 이동을 브라우저에서 확인한다. 도구 제약으로 실행하지 못한 검사와 통과한 검사를 구별한다. 첫 단계 소스를 읽지 못하면 앱을 수정했다고 보고하지 않는다.

## 기준 전환 및 기존 코드 개편 요청 v0.4

### 1. 기존 대화에서 반영할 수 있는가?

기존 코드가 있는 대화는 구현 맥락을 보존하기 좋다. 우선 그곳에서 새 기준을 명시하고 구조가 실제로 바뀌는지 확인한다. 큰 구조 변경이 계속 색상·카드 수정으로 축소된다면 새 대화에서 현재 코드를 이어받는 방식이 더 명료할 수 있다. 새 대화를 열어도 같은 프로젝트의 공통 지침·자료가 그대로라면 충돌은 남을 수 있다.

Claude 공식 도움말은 프로젝트에 올린 자료를 대화의 문맥으로 사용하고, 프로젝트 지침을 해당 프로젝트 대화들에 적용한다고 설명한다. 따라서 프로젝트를 사용하는 경우 채팅 메시지뿐 아니라 프로젝트 공통 지침·참고 자료의 이전 배치 지시도 점검한다. 문서 교체가 코드·배포 결과를 자동 변경하는 것은 아니다.

```text
- 03: 개별 작업 내부의 정보·행동·결과만 설명한다.
- 00: 범위와 문서 적용 방식을 정한다.

현재 프로토타입의 소스를 먼저 읽어. 공유 화면만 보거나 이전 대화를 기억하는 것으로 코드 확인을 대신하지 마. 코드를 읽을 수 없다면 필요한 파일·프로젝트 접근을 정확히 알려줘.

이번 응답에서는 코드를 수정하지 말고 다음 다섯 가지를 간단히 보여줘.
1. 현재 실제로 읽은 코드·문서와 수정 가능한 범위.
2. 폐기하는 이전 배치 규칙과 보존할 기능·저장 규칙.
3. 서비스 홈→크루 홈→미션 목록→미션 상세→퀵 리뷰의 연결도.
4. 기존 화면·컴포넌트를 각 페이지에 어떻게 옮기고 어떤 업무 로직을 재사용할지.
5. 데이터 호환과 기능 보존을 확인할 T 테스트, 구조 개편을 확인할 U 테스트.

전체 앱 앞에 홈 화면 한 장만 추가하거나 목록을 카드로만 바꾸는 계획으로 답하지 마. 미션 상세에 속한 퀵 리뷰 작업 페이지와, 크루원이 사용하는 독립 상세 페이지를 명확히 구분해.
```

#### A 응답 확인 기준

- “새 문서 이해했다”는 선언만으로 통과시키지 않는다.
- 다섯 페이지가 구별되고 퀵 리뷰에 선택 미션·돌아갈 경로가 있는지 확인한다.
- 현재 코드를 실제로 읽었는지, 추정하는 부분은 무엇인지 확인한다.
- 데이터 삭제·전체 재생성·프레임워크 교체가 기본 계획에 들어가지 않아야 한다.
- 1차에 관리자·성과·소통 전체를 자동 추가하지 않아야 한다.

### 4. B — 기존 코드에 적용 요청: A가 맞으면 붙여 넣기

```text
확인한 v0.4 기준과 구조에 따라 기존 프로토타입을 개편해.

기능 F-01~06, F-08 공통 집계, F-11A와 현재 이미 구현된 기능을 보존한다. 현재 저장 키·형식·ID·제출 버전·피드백 이력을 유지하고, 화면 변경을 이유로 기존 데이터를 초기화하지 마. 아직 구현하지 않은 이후 단계 기능은 이번에 추가하지 마.

먼저 현재 기능·화면·저장·검증 명령의 기준 상태를 기록한다. 다음 책임을 분리하되 기존 코드가 이미 분리돼 있으면 재사용한다.
- 앱 공통 틀과 전역·크루 메뉴
- 서비스 홈·크루 홈·미션 목록·미션 상세·퀵 리뷰 페이지
- 공통 표시와 입력·이력 컴포넌트
- 조회·집계·상태 전환 명령·저장

기존 환경과 프레임워크를 유지한다. 메뉴·페이지 선택 상태와 업무 데이터, 미저장 입력을 구분한다. 미션·사용자 이름을 ID로 사용하지 않는다. 저장 성공 이후만 상태를 확정하고 실패 시 입력을 유지한다.

전체 서비스→크루 공간→미션 상세→퀵 리뷰 계층을 실제 페이지 이동으로 구현해. 크루원 상세에는 기존의 왼쪽 목록을 계속 붙이지 말고, 퀵 리뷰의 제출자 목록·상세 병렬 구조만 보존한다. 시연 도구는 접을 수 있게 하고 실제 인증·알림 발송으로 표현하지 마.

미션 등록, 텍스트/링크 제출, 피드백·수정본, 처리 직후 읽기 전용 결과, 다음 검토, 알림의 연결 버전 이동, 미저장 입력 이탈 확인을 빠뜨리지 마. 기존 로직을 성공 화면으로 대체하지 마.

홈·크루 홈은 현재 사용자에게 허용된 원본 데이터의 조회 화면으로 만든다. 가상 성장 점수·랭킹·추천·빈 미래 메뉴를 추가하지 마. 소통·성과·제안은 01에서 정한 확장 위치만 유지한다.

U-01~08과 현재 구현 범위의 T 테스트, 타입 검사·빌드·저장 실패·중복 처리·새로고침 유지 검사를 실행해. 390px와 1280px에서 주요 페이지·빈 목록·긴 제목·오류·버튼을 확인해. 실행하지 못한 검사는 미확인으로 보고해.

최종 보고에는 바뀐 페이지, 유지한 기능 ID, 이전 규칙이 제거된 위치, 저장 호환 여부, 검증 결과와 남은 제한을 적어. 이후 단계는 자동으로 시작하지 마.
```

### 5. 기존 대화에서 계속 이전 화면이 나오는 경우

새 대화는 기존 코드의 폐기가 아니라 **현재 코드 + 새로운 문서 기준의 재전달**이다.

- 활성 프로젝트 지침·자료에서 옛 기준이 남아 있는지 먼저 점검한다.
- 새 대화에는 현행 소스·실행 방법·현재 구현 범위·저장 키/형식·테스트 정보를 함께 제공한다.
- 대화 전체를 복사하지 않는다. 새 기준과 충돌하는 오래된 설계는 넘기지 않는다.
- 과거 화면 캡처가 필요하면 “변경 전 현황이며 목표 디자인이 아님”이라고 표시한다.
- 원래 앱과 데이터의 사본은 별도 보관한다. 새 대화에서 소스 없이 기존 기능이 자동 복원될 것으로 기대하지 않는다.

새 대화 첫 문장 예:

```text
첨부한 소스는 보존할 기능을 가진 현재 앱이며, 현재 레이아웃은 교체 대상이다. 목표 구조와 업무 규칙은 첨부 v0.4 묶음만 기준으로 삼아. 먼저 04의 A 기준 전환 확인을 수행해.
```

### 6. 이 문서의 적용 상태

현재 Claude 프로젝트·대화·지침·코드를 직접 수정한 문서가 아니다. 새 기준 전달과 실제 코드 개편, 배포 결과 확인은 별도 실행 단계다. 기준 전환만으로 원하는 구현이 보장되는 것은 아니므로 계획과 실제 U/T 결과로 확인한다.
